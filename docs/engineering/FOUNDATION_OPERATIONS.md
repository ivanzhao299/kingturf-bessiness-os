# Foundation operations runbook

Every response exposes `x-correlation-id`; use it to locate the immutable audit record. `/health` is process liveness and `/ready` verifies PostgreSQL. Logs and metrics may contain bounded operation names, states, timings, and correlation IDs, but never bodies, tokens, file contents, notification text, or event payloads.

For notification incidents, inspect recipient and delivery-attempt state by tenant; external channels remain `DISABLED` or `UNCONFIGURED`. For attachments, reconcile stale `PENDING` metadata and temporary storage, then logically delete metadata before cleaning bytes. Never place bytes in PostgreSQL.

For events, inspect tenant-qualified state counts and consumer-specific delivery state, attempt history, lease expiry, and `last_error_code`. Secured worker operations are `POST /api/v1/operations/events/claims` and `POST /api/v1/operations/events/{eventId}/{complete|retry|dead-letter}`; tenant identity always comes from the authenticated actor. Each lease has a fresh claim token, and only that unexpired token may complete or fail the delivery; never log or persist the token outside the delivery row. A delivered checkpoint belongs to one named consumer and never suppresses another. Resolve the underlying dependency before administratively replaying a dead letter; retain attempt history and consumer checkpoints. Migration recovery starts with `pnpm db:status`: drift is a stop condition—restore released bytes rather than editing migration history.

Attachment writes use token-fenced, five-minute upload leases and token-specific local-adapter keys. An expired `UPLOADING` row can be reclaimed; only the current token can finalize or reset it. Deletion first commits an audited `DELETE_PENDING` reservation, then removes bytes, then transactionally records `DELETED` and its audit. A storage error deliberately leaves `DELETE_PENDING`; retry the same delete with the pre-delete or current version after restoring storage. Never update these rows manually, because doing so bypasses lifecycle audit evidence.

Local attachment storage requires the explicit `ATTACHMENT_STORAGE_ADAPTER=local` and `ATTACHMENT_LOCAL_DIRECTORY` settings. Configuration rejects the local adapter in production until a reviewed production adapter is implemented.

Local release evidence is produced with `pnpm ci:local`. It consumes only the ambient Studio loopback PostgreSQL test fixture (or an equivalent explicitly supplied local fixture), scopes `NODE_ENV=test` to the command, and never loads, writes, or prints a secrets file. The database guard still requires a loopback host and a database name containing a `test` segment before migration. The command runs frozen install, formatting, lint, strict typecheck, migration apply/status, zero-fallback test execution, build, and high-severity production dependency audit.
