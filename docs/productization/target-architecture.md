# KingTurf V1.0 目标技术架构草案

推荐保持模块化单体，复用现有Node24、pnpm10.33.4、TypeScript、Vite原生DOM、node:http和PostgreSQL17。基线 `b1ef7a9` 已建立会话、SQL范围、不可变版本、事务、审计和机械门禁；当前问题不足以支持整栈替换。采用“保留主体，局部改进有证据的不合理部分”，总体计划批准后才实施。

## 三方案比较

| 维度       | A 保留并优化                             | B 分阶段局部迁移                          | C 全面替换                               |
| ---------- | ---------------------------------------- | ----------------------------------------- | ---------------------------------------- |
| 开发效率   | 熟悉现有端口与测试，短期投入最低         | 可独立改善复杂表单/路由/读模型，需兼容层  | 大量平台功能重建，初期业务产出低         |
| 维护与生态 | 手写路由/DOM工具需自维护，依赖少         | 仅在重复性成本证明后引入成熟组件/边界工具 | 框架生态广但迁移、适配与升级责任明显增加 |
| 性能       | 现有登录预算和按路由加载保留；先测慢查询 | 定点优化分页、聚合、后台长任务            | 不保证改框架就提升SQL或业务事务性能      |
| 风险与兼容 | 最利于生产数据及不可变模型兼容           | 双路径需契约与灰度，控制范围后可回滚      | 权限、金额、历史数据、DOM行为回归面最大  |
| 测试代价   | 已有回归为基线，补业务缺口               | 每子域旧新契约与独立对账                  | 全链全角色和迁移恢复需重建证明           |
| 扩展性     | 清晰端口/事务边界可继续增长              | 为确证热点提供更成熟抽象                  | 未证组织规模需要重服务化或新数据库       |
| 结论       | 当前默认技术栈                           | 推荐的局部改造方法，具体选型另ADR         | 当前不批准、不排为V1前提                 |

任何框架/运行时依赖引入须以测得的人力/质量收益、维护能力和授权为依据，不能凭流行度。ADR0001偏好零框架不是禁止重新评估，但修改该决策需新ADR、兼容与回滚批准。

## 前端后端和数据访问分别比较

以下为架构候选评估，不是已批准的库选型。当前工作区的实际依赖见根及apps/api、apps/web、packages/database的package.json；不把框架生态优势直接等同于业务正确性。

| 领域          | A 保留优化                                                                                             | B 渐进迁移                                                                                          | C 全面替换                                                                                                       | 推荐和验收门槛                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 前端框架/状态 | 保留Vite/DOM和SessionContext；改具名读模型、分页、表单意图；兼容与回归代价最低，自维护工具成本继续存在 | 仅对已量测的复杂表格/表单页面引入组件或状态库；生态可减少重复开发，但双路径需生命周期/会话/焦点隔离 | 整个SPA转框架；工具生态成熟度可能提升，但须重证所有权限投影、异步代际、单据交互、启动预算和移动端                | 选A为默认、B为后续候选；先取实际岗位/性能基准。页级灰度、契约/键盘/会话回归和旧路由回切通过后才扩大 |
| 后端HTTP/路由 | 保留node:http，提取职责明确的路由装配，复用现有认证/校验/授权/错误与telemetry                          | 单独替换反复出现且维护成本有证据的路由/校验基础设施，保持ApiRequest/Response和仓储端口合同          | 全面迁移后端框架；可获得路由/中间件生态，但默认错误、body解析、代理信任、Cookie和事务时序差异需全量重证          | 选A，B需量测与ADR；必须比对状态码/DTO/权限/审计/幂等及真实HTTP拒绝，不能把框架迁移当修复SQL         |
| 数据访问/迁移 | 保留pg、参数化SQL和手写append-only迁移；在热点收敛可信SQL片段和投影类型                                | 只在确证收益的读模型试点类型化查询工具；复杂财务/库存写事务保留已有约束，避免两个事务管理器         | 全部迁移ORM或替换数据库；维护模式可能统一，但租户组合键、不可变触发器、numeric精度、锁和迁移checksum迁移风险最高 | 选A；B须同真实PG数据比较结果、事务/并发/查询计划与参数化护栏。C无当前收益证据，生产兼容迁移另授     |
| 外部集成/后台 | 保留事务outbox和最小适配器，有界执行/重试与人工异常队列                                                | 按实际会计/物流接口建立单方向、版本化合同与对账；明确一个主写方                                     | 先建通用集成平台或拆多个服务会增加部署、幂等、链路故障与运维成本                                                 | 无接口需求不新增基础设施；先确定权威系统、量级、失败语义和支持责任                                  |

上表分别处理开发效率/生态和维护收益；总体比较表中的兼容、可靠性、迁移风险、性能和回归成本仍是统一决策标准。A也必须补齐自维护设施的业务测试，不能因为当前依赖少就默认合理。

## 领域和依赖

目标领域为身份组织/权限、CRM、技术与CPQ、商务与经营资金、制造主数据与计划、生产与质量、库存履约、售后催收、平台审计与附件。包级保持 `apps/api→packages/{config,database,domain,types}`、`domain→types`；仓储不反依赖服务，包不反依赖apps。当前跨域事务应由已登记端口的Service编排；单仓路由可直调Repo，不添无意义透传。

前端保持 main→entry→workspace-loader→bootstrap→各域→共享原语。把通用列表从DOM文本推断改为类型明确的读模型；服务器分页/排序/筛选口径与导出一致。待办读模型复用领域状态、责任与审批记录，避免前端另造状态机。保留SessionContext所有权、异步代际检查、固定重试意图、请求去重与HTML清洗；缓存优化先测正确性和收益。

后端保留原生HTTP统一认证、校验、授权、错误、correlation及telemetry入口；按职责继续提取长路由装配。声明式校验是否采用新库待重复成本评估，边界改变先登记。关键写操作将状态、库存/金额、审计、outbox和幂等结果放同一事务，锁范围由冲突模型决定。不得以增加Service来掩盖SQL缺陷。

PostgreSQL继续参数化、租户组合FK、唯一约束、乐观锁、不可变守卫及append-only迁移。生产来源与发运数量先做约束设计，再评估已有数据兼容；不允许未经审批直接加约束后自动修生产数据。数据库迁移编号由主控统一，新增迁移和补偿前滚策略单独审查。

## 候选ADR和批准边界

| 主题               | 决策内容与前置证据                           | 兼容/回滚                                              |
| ------------------ | -------------------------------------------- | ------------------------------------------------------ |
| 订单到制造履约来源 | 订单行、需求分配、超产与补货身份；候选MRP002 | additive关联先读写兼容；旧自由文本保留，不回填未证关系 |
| 发运与库存原子事务 | 分批、拼单、批卷、预占/出库、累计量、公差    | 新旧命令受控切换；既有证据不可删除，纠错用补偿         |
| 四层成本与利润     | 实际计价、分摊、币种、关账和晚到费用         | 新口径新版本，旧报表保留口径标签，禁止重写历史         |
| 幂等意图与响应丢失 | 意图ID生命周期、重试、冲突、结果恢复         | 兼容旧header/命令指纹，新行为单独授权                  |
| 局部前端或校验库   | 仅经基准证明的复杂操作热点                   | 页面级替换、契约及键盘/权限回归、可回切旧路由          |

本轮只形成ADR议题，不创建“Accepted”决策或修改ADR0003/0004/0009/0010。CSP报告/强制切换、正式监控及发布审批另走生产授权，不随代码重构激活。

## 性能和后台处理

先由业务量定义列表条数、并发岗位、峰值操作、附件大小与报表周期；测p50/p95、错误率、SQL计划/锁等待、连接池、内存和前端请求数。对全量读与已登记N+1逐项优化，不提前建缓存集群或拆微服务。长报表/外部同步可复用outbox和有界worker，明确幂等、重试、失败队列和关闭行为；未确认需求不新增队列平台。
