## 新发现：TD-INV-001 库存并发阻断

0038_procurement_inventory_integrity.sql:44–52在INSERT前SUM可见流水后核非负，没有同批次库位串行锁；procurement-repositories.ts:513–575也没有。新真实PG合成测试以初始10，用原move发起两笔ISSUE7：两个事务均完成原SQL、audit/outbox后停在提交前屏障，再共同提交，余额为−4，各有一组完整证据。没有修改触发器/约束/库存数值，屏障只制造合法重叠事务；独立源码复核确认机制。

这是当前库存非负保护的并发缺陷，非Batch1采购收货回归；Batch1只锁同一采购单的收货。P1试运行阻断，真实生产负余额尚未检查，不宣称生产已超发。本批只登记和重现，不改正式过账。未来不能只给新发运接口加锁，必须覆盖所有负向移动和并发组合。

## A/B方案比较与推荐

| 维度           | A 单独确认仓库出库                           | B 确认发运时自动出库                             |
| -------------- | -------------------------------------------- | ------------------------------------------------ |
| 唯一扣库动作   | 仓库确认出库事务                             | 发运确认事务；创建草稿仍不扣库                   |
| 物流与仓库职责 | 支持分岗、装车后待承运和分票                 | 适合同岗一次确认                                 |
| 发运关联       | 运单分配已确认出库行，不能再次扣库           | 运单确认同时写出库行和移动                       |
| 取消           | 确认前释放预留，确认后按实物退回追加移动     | 确认前取消草稿，确认后同样走实际退回             |
| 风险/成本      | 多一类明确业务单据，链路可追溯               | 界面较短，但现场装车和物流录单不同步时容易误过账 |
| 当前适用证据   | 角色目录有仓库和物流职责，但不能证明实际分岗 | 尚无同岗确认的业务证据                           |

条件性推荐A：发货放行是允许拣货的业务许可，仓库确认出库唯一扣库；物流引用已出库可分配量。若负责人确认同岗同动作，则B可采用相同出库命令与底层事务，仅由发运确认触发。若已有外部WMS为库存权威，先定义唯一外部出库标识和对账，不并造两份权威账，不预建复杂集成平台。

## 数量模型和单据关系（提案）

| 对象                                     | 关联及最小数据                                                                                          |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| order_fulfillment_lines                  | 销售订单行→已确认产品/规格版本、订单/基础单位、批准换算、可履约量；当前订单行缺成品版本，不可从描述猜测 |
| outbound_orders / lines                  | 原销售订单行、放行申请、批次/卷号、库位、基础数量、单位、version、状态；跨租户复合FK                    |
| inventory_reservations（若业务确认预留） | 对原批次库位/订单行的预留数量、到期/释放事件和幂等意图；不改变现存物理流水                              |
| outbound_postings                        | 出库确认行→唯一负库存movement、原动作和intent ID；unique(tenant,outbound_line,posting_kind)             |
| shipment_lines                           | 运单→已确认出库行及分配数量；能一单多票/多批，一次物理出库不重复扣库                                    |
| return_receipts                          | 原出库行→实际退回数量/新检验状态/唯一正向补偿movement；不删除旧出库                                     |

数量不变式：物理on_hand=不可变流水和；可用量=符合放行质量的物理量−有效预留；同一订单行累计确认出库≤批准可履约量（超发公差待裁，不能默认为允许）；同一放行累计分配≤批准量；同一出库行累计装运≤其确认数量；签收≤装运；累计退回≤可退且实物已收数量。取消是否恢复订单可履约额度，须与实际补偿及重新发运规则绑定，不能只减计数。

库存基数可能是M2/KG/长度，卷号可能带实际幅宽/卷长。所有比较使用明确基础单位和批准换算版本，不自动将订单文本、卷数和面积等同；BOM已批准产出基数不在此重议。

## 幂等、并发和事务

稳定业务意图ID在表单首次提交前生成并持续保存；网络丢响应先查命令结果，不能为重试另造意图。重放先按原命令对象执行当前权限，合法返回原结果、无二次移动；同键异主体/数量等输入冲突，不能改原单静默再扣。

A的确认事务：授权→命令锁及原对象重放授权→按固定顺序锁订单行额度/放行/出库单→排序锁批次库位→重验实时门禁及可用量→写唯一库存移动、确认行/状态事件、审计/outbox/命令结果→提交。B在同一事务同时写运单确认，不分两次提交。失败后不留下已扣库未确认或已确认未扣库；外部物流通知走提交后outbox重试，不把第三方HTTP放在持锁事务内。

TD-INV-001首选最小独立方案可评估新迁移在库存门卫检查前锁共同批次（较粗但覆盖旧写入），或原子批次库位余额守卫；备选物化余额表改动较大。必须实测等锁后的可见快照，不能凭“加了FOR UPDATE”宣称正确。多批/多库位先按(tenant,lot,location)排序取锁，生产、手工移动、出库共用策略，拒绝skip-locked漏核或不存在余额行漏锁。业务根对象与库存锁的全局顺序也须统一，避免反序死锁。旧应用及所有直接合法写入必须经过同一有效门卫，不能靠新增API独自保证。

## 门禁、异常和回退

建议将门禁分为不可例外的隔离/非法组织/单位或实物不足，以及有期限、有金额/数量范围的商业例外；具体质量、信用、回款和成本要求待负责人确认。例外应绑定源版本/数量/审批人与有效期，确认出库时重验；新出现的问题不能由旧泛化审批自动覆盖。

确认前取消可释放尚有效的预留/分配；确认后物流取消不自动加库存。实际回仓时追加退回收货与质量隔离证据，退回数量核原出库累计，重复收货恢复同一结果。承运异常、丢货、部分签收、拒收和质量投诉分别有事件及责任，不把POD状态当库存调账。数量差异、退货损失及运费归经营成本待财务口径，不擅自计价。

历史运单缺数量/精确出库关联，标LEGACY_UNRECONCILED；不因原申请量5有两票便回填10或强行只认一票。先保留只读历史、独立人工对账和批准映射，新模型可限新业务切入。新迁移append-only，原库存流水不改；产生新过账后回退必须保留认识新单据和防重复的兼容构建，业务纠正用补偿而非删流水。生产迁移、负余额修复和真实恢复均另授。
