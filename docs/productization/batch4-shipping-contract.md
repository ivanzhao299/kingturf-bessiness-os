# Batch 4 仓库出库与分批发运定稿提案

**DESIGN_ONLY，未批准改变正式库存过账或发运状态。** 沿Batch2/3，首选方案A：商业/质量放行→仓库拣配→仓库确认出库唯一扣库→物流分票发运→POD。方案B仍是备选“发运确认与出库同事务”，不是把扣库插入现行创建运单动作。当前dispatch创建即DISPATCHED，运单无数量行且不扣库（shipment-repositories.ts:201–258、0050:54–73）；没有生产业务访谈证据证明哪岗实际扫码/称重/装车，本提案须由仓库和业务负责人裁定。

## 稳定决策与数量定义

沿Batch2：S1过账岗位/动作，S2分批及单位，S3门禁和例外，S4预留，S5取消/退回。Batch3曾重排S2–S5，不能据该代号转移批准；签收为S5.a、额度恢复为S5.b等明确子项。

| 业务量           | 权威与含义                                                 | 不可混用                                          |
| ---------------- | ---------------------------------------------------------- | ------------------------------------------------- |
| A 已批准可发数量 | 放行行及后续批准调整的额度账；绑定订单行、单位及版本       | 不是库存预留、运单数或当前仓库余额                |
| C 已创建发运数量 | 数量行创建的毛累计；另列草稿、已取消、有效分配、已离库装运 | 创建记录不等于出库/实际发出，取消不删除原创建事实 |
| O 实际出库数量   | 唯一POSTED仓库出库行的毛累计，逐行关联负库存移动           | 不在物流分票时再次扣库，退回不改写O的历史         |
| D 已签收数量     | POD行接受量毛累计；拒收/短少/损坏单列                      | 不等于C/O；退货不删除原签收事实                   |

订单可履约量、预留量R、未发退回量、发出后退回量是额外独立账。Batch3“净装运分配≤净出库”公式不适用于退货后的历史对比：出库/发出10、回仓2，历史发出仍10，不能拿它与净8比较。本方案纠正提案，不修改历史业务数据。

每出库行固定o_i；分配消耗a_i=有效ASSIGN−允许的离库前RELEASE，已发/已交付不会释放原分配消耗。未分配且真实回仓量u_i另记。新分配上限为o_i−a_i−u_i；发出后客户退货不再次释放旧出库行容量。退回货经检验入库后若重发，须新出库及明确的补发授权，不能重复使用旧分配行。

订单/放行额度独立用批准、消耗、撤销未用、批准恢复事件计算剩余。新POSTED消耗额度；S5.b必须裁定离库前实物退回是否恢复额度、由谁批准；客户退货默认不自动恢复发运额度。不能把历史毛出库简单相减当作可再次发货量。所有额度转换使用冻结计量单位和换算版本；整卷不可任意拆分，实际切卷需新卷号/分割证据。

## 推荐状态、岗位和门禁

仓库候选状态DRAFT→PICKING→POSTED；未过账可CANCELLED，已过账不可改量/删流水，纠错走关联原单的补偿。物流候选DRAFT→CONFIRMED→DISPATCHED→IN_TRANSIT→PARTIALLY_DELIVERED/DELIVERED/EXCEPTION；另有CONFIRMED→CANCELLED发车前取消终态（禁止再DISPATCHED）；离库后不能普通取消恢复库存。上述为新增模型建议，不能冒称现行枚举已有这些状态。

S1推荐仓库受权岗位确认实物出库；放行岗验证商业/质量条件，物流岗操作分票/运输/POD。当前库存控制、仓库放行、物流跟踪权限并不相同（0046:85、0050:115–123），不直接把inventory:move授给物流。S2推荐允许分批，按精确订单行→放行行→出库行→运单分配行控制数量，不用“已有一张运单”隐藏合法后续操作。

S3推荐放行、出库和装运三个适用点重核有效合同/订单、质量批卷状态、信用与回款限制、成本有效版及例外有效期。质量不合格/隔离不得靠普通审批绕过；哪些商业例外可由谁批准须业务裁定，证据须绑定具体对象、数量、期限和批准人。已出库而装运前信用失效时，进入暂存/异常待办，不能为方便恢复库存或复用过期放行。

S4首版推荐商业放行不预留库存，仓库草稿显示“可用量为当前查询，未保证”；POSTED时数据库重新校验。若企业需要拣货预留，应另有预留事件、过期/释放、可用量定义和并发保护，不能把放行数量或运单草稿伪装成预留。该选择仍待负责人批准。

## 数据、API与事务

建议新增warehouse_issue头/行、quota_events、shipment_allocations、POD行和return_receipt行；每行绑定tenant、订单行、放行、产品/物料版本、批/卷、库位、源单位与换算。出库行与库存移动唯一关联，补偿引用原移动；重复意图键绑定原主体/动作/请求指纹，当前动作权、read范围和fields分别复核。

建议API：POST /warehouse-issues创建草稿、/:id/post确认；运单创建为草稿，/:id/confirm分配可装运量，/:id/dispatch记录离库，/:id/pod分行接受/拒收，退回用独立收货接口。均带expectedVersion、原因/证据、幂等键。是设计端点，不是对现有接口合同的立即替换。

POSTED事务按稳定顺序锁订单额度→放行/出库资源→库存资源，锁内复核剩余、当前门禁和版本，原子写出库/额度消耗/唯一库存移动/审计/outbox。运单分配另锁确切出库行并核剩余，不再扣库。使用数据库跨连接并发控制；Batch3库存保护仅解决非负，不解决订单或运单上限。反序多资源可能死锁，须稳定锁序、完整回滚及明确整事务重试，不写“绝无死锁”。

S5：未过账取消可释放尚有效预留/分配；已过账取消须先确认实物位置，物流状态不能自动增库。实际回仓按原出库可退上限、批卷及质量记录正向退回移动，幂等重复不重复入库；不回写O/C/D毛历史。部分POD把接受、拒绝、短少、损坏分别记录，已接受后退货另单。库存退回、额度恢复、收入/应收冲减及费用损失是不同动作，不能由一个取消按钮隐含完成。

## 工作台、对账和兼容

仓库工作台：待拣/待确认、批卷/库位可用量、门禁失败原因、已出库/未分配/已分票和待退回；确认前展示数量与后果，失败保留输入，同键查结果。物流工作台只用可分配的已出库量，支持多票、追踪、POD、异常责任和证据。每条单据可导航订单、放行、出库、移动、运单、签收与退回，不依赖prompt或手工SQL。

独立账分别核对：订单额度消耗；放行剩余；每出库行唯一负移动；分配消耗+未发退回≤毛出库；POD接受/拒收/差异≤实际发出；累计实物退回≤可退原出库/交付；库存余额=所有正负流水。经营退货/成本计价另按财务批准口径归集，防重复计损。

历史运单没有可靠数量关联则LEGACY_UNRECONCILED，只读保留，不按订单量或票数猜测、补扣库或改DISPATCHED历史。新模型限批准的新业务切入；向前迁移、旧API兼容层、并存写禁用和识别新状态的回退构建必须先验证，不能让旧程序重复发货。生产数据映射/迁移/恢复分别授权。

验收：10分4/2/4、11超发、同键并发、不同意图7+7、跨仓/批/卷/组织、整卷拆分拒绝、质量隔离、信用变化、例外过期、移动或审计晚失败、丢响应同键确认、取消货未回、部分签收、发出10回2不释放旧分配、实物退回与新补发、历史未知数量。真实PG同步屏障、HTTP权限及仓库/物流岗位人工验收缺一不可。

实施前最小裁定：S1选择A/B及实际岗位；S2分批、单位/卷分割、公差；S3绝对门禁/例外；S4是否预留及生命周期；S5/S5.a/S5.b取消、签收、实物回仓和额度恢复。正式业务尚未获批，SHIPPING_INVENTORY=DESIGN_ONLY。

## 独立复核补充边界（仍待S2/S5批准）

候选物流CONFIRMED但尚未DISPATCHED时，允许有取消权的仓库/物流岗位将其转为CANCELLED，并在同一事务释放原出库行上的分配消耗a；仓库已POSTED的库存不恢复，也不自动产生退库移动。取消与发车锁定同一发运及分配行，CANCELLED永不再允许DISPATCHED；需要再发则新建分配和发运。已发车后的取消仅作异常记录，走实际退回及补偿，不能释放历史分配。

候选DISPATCH操作一次冻结并发出该CONFIRMED发运的全部确认分配行数量，持久化不可变dispatch_line_quantity作为实际发出量。不能用创建毛量C或仓库毛出库O代替。部分装车必须先在发车前重新分配/拆分成多个确认发运；若企业需要同一物流单多次发车，改为独立发车批次模型另裁。POD累计签收不得超过相应发车行实际量；回退不改已发车历史数量。
