# Batch5 业务规则审批契约

状态：**DESIGN_ONLY**。本文件将 Batch4 的 M1、C1–C4、S1–S5、V1、P1–P2 转换为最小可批准规则；批准前不修改正式金额、成本审批、库存过账、BOM 或利润归集。

## M1 金额精度与舍入

推荐：数量和分钟沿用现行最多 6 位输入及既有 trunc6 业务语义；中间计算使用定点十进制/BigInt，不经过 JavaScript Number；金额分项量化到 6 位，分项存储后求总额，负值采用 HALF_AWAY_FROM_ZERO，负零归一为 `0.000000`。历史 run 不重算；新 run 写入 calculation_version、舍入模式、币种和汇率依据。

备选：HALF_EVEN。税基、币种小数位、汇率来源/方向/时点必须作为单独字段确认，不能使用默认值。审批阈值沿用现有异人审批，Batch5不新增金额阈值。

必须确认：舍入模式、负数 tie、数量/分钟 trunc6 是否保持、FX/税基来源、旧单据是否完全冻结。TD-COST-003 的重复组件计量必须先按本批复现结果另行裁定。

## C1–C4 成本驳回修订

- 只有未关闭工单的当前 REJECTED run 可创建修订；原 run 不可变。
- 原申请人或授权核算岗可创建 r2；审批人必须与本次申请人不同。
- 新 run 保存原 run、BOM/政策/价格快照和 calculation_version；同一工单最多一个 current candidate。
- r2 计算成功后进入 CALCULATED，只有 r2 APPROVED 才允许关单或发运；不回落旧 APPROVED。
- 幂等键绑定工单、expectedCurrentRunId 和修订意图；竞争返回 409，历史报价/订单/工单继续引用精确 run。
- APPROVED 或 CLOSED 业务走独立调整单；首版不引入撤回状态。

必须确认：申请人能否再次提交、关闭单据的调整流程、current candidate 唯一约束、批准/拒绝 API 的错误合同及迁移策略。

## S1–S5 发运与仓库

推荐方案 A：发运放行、仓库出库确认、物流发运和签收分别建账。仓库授权岗位确认实际离库并在 POSTED 时扣库存；发运创建不扣库，首版不预留物理库存。方案 B（发运确认自动扣库）暂不推荐，会把物流职责与库存账务耦合。

每条订单/放行行分别记录批准量 A、发运创建毛量 C、实际仓库出库 O、实际发车 D、签收量 P。允许分批，累计 O/D/P 均不得超过对应允许量；重复请求以业务意图幂等键和来源单据唯一性防重。CONFIRMED 可在 DISPATCHED 前由授权岗位取消，释放未发车分配；POSTED 库存不恢复，实物退回必须走检验和补偿入库；CANCELLED 禁止再次 DISPATCHED。质量、信用、合同门禁在放行、出库、发车各适用点重核。

必须确认：S1岗位、S2单位/卷拆分和公差、S3异常批准人、S4是否引入有时效 reservation、S5.b退回后订单额度是否恢复。验收必须包含 10=4+2+4、重复提交、并发 7+7、取消/退回和独立订单库存对账。

## V1 BOM 冻结

推荐在工单正式 RELEASED 事务内冻结完整多层 BOM manifest，记录 releaseAt、knowledgeAsOf、输出基数、单位、损耗、替代料和来源版本；MRP、生产和成本均引用该 manifest。工单草稿可预览但不冻结。工程变更只影响尚未领料/报工的剩余工作，追加新 manifest 或拆分执行批次；历史缺失版本标 UNKNOWN，不回填 latest。多个同 effective 候选必须拒绝自动下达并要求技术岗位显式选择。

必须确认：工厂业务时区、创建/下达哪个时点作为冻结点、已领料/报工后的变更权限、替代料和单位换算规则。

## P1–P2 实际订单利润

V1 同时展示报价估算毛利、标准成本经营毛利、实际耗用政策计价毛利和最终结算利润。每项成本标记 ESTIMATED、ACCRUED、ACTUAL 或 REVERSED；缺失不填零，估算不允许把订单标记为 COMPLETE。制造成本、物流、佣金、质量损失、销售费用、应计和冲销分别关联权威来源；法定收入、税务和账务仍归外部财务系统。

必须确认：收入确认事件、材料估值政策（冻结政策价/FIFO/移动平均）、物流和佣金来源、共享工单分摊、晚到费用、退货/佣金冲销和关账后追补责任人。

## 审批与回退

每项批准记录负责人、日期、适用版本、示例期望值和不适用场景。批准前保留现有实现与历史数据；正式实施按独立提交、隔离迁移、PG/HTTP/岗位验收和可回退提交执行。任何方案批准不包含生产部署、远程推送或主线合并。
